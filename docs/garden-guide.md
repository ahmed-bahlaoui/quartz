# Managing My Digital Garden — The Complete Guide

This file explains exactly how your Quartz digital garden works end-to-end, how to publish updates, and the things worth knowing. Read it top to bottom once, then keep it as a reference.

---

## 1. What is Quartz?

Quartz is a **static site generator** for Markdown notes. It is *not* a CMS with a database and admin panel. Instead:

- You write plain Markdown files (like in Obsidian).
- Quartz **builds** them into plain HTML/CSS/JS files.
- The generated files (the `public/` folder) are hosted as a static website.

Your whole garden is text files. That is its superpower: no server, no DB, version-controlled with Git, and free to host.

Your site lives at: **https://ahmed-bahlaoui.github.io/quartz/**

## 2. The Pipeline (end to end)

Here is the full journey from writing a note to it appearing on the internet.

```
[write .md file]  -->  [quartz build]  -->  [public/ HTML]  -->  [git push]  -->  [GitHub Actions]  -->  [GitHub Pages]
```

### Step 1 — Write a note (the source of truth)
You write Markdown in `content/`. This is the *only* place you ever edit. Anything you write here is the real content — HTML is just generated from it.

- `content/index.md` — your landing page (main page).
- `content/<folder>/<note>.md` — any note, in any folder structure you like.
- Images go in an `images/` subfolder next to their note.

### Step 2 — Build locally (`npx quartz build`)
This converts Markdown → HTML into `public/`.

- Reads all `.md` files under `content/`.
- Processes plugins: LaTeX (`$$`), wikilinks (`[[...]]`), syntax highlighting, tables of contents, **the graph**, backlinks, images, etc.
- Emits static HTML + hashed CSS/JS into `public/`.

```
npx quartz build
```

You run this to *preview* locally and catch errors before publishing.

### Step 3 — Commit & push (`npx quartz sync`)
`sync` is the convenience wrapper around Git:

1. **Pull** — fetch the latest changes from GitHub (so you don't overwrite others/edit-from-another-device work).
2. **Stage** — stage all modified/new files.
3. **Commit** — create a commit with your changes.
4. **Push** — upload to GitHub.

```
npx quartz sync              # pull + add + commit + push
npx quartz sync --no-pull    # first time, or your remote is ahead/empty
npx quartz sync -m "my message"
```

> `public/` is **gitignored**. It is regenerated by GitHub Actions on every push — you never commit the built site. That keeps the repo clean (source only).

### Step 4 — GitHub Actions auto-builds & deploys
The file `.github/workflows/deploy.yml` registers a workflow named **"Deploy Quartz site to GitHub Pages"**. It runs on **every push to the `v5` branch** (your default branch). What it does, in order:

1. Checks out the repo (full history, so Git-based dates work).
2. Installs npm dependencies (`npm ci`).
3. Installs Quartz plugins (`npx quartz plugin install`).
4. **Builds** the site (`npx quartz build`) — regenerates `public/` in the cloud.
5. Uploads `public/` as a "Pages artifact".
6. Deploys it via `actions/deploy-pages` to the `github-pages` environment.

### Step 5 — GitHub Pages serves it
Once deployed, GitHub serves `public/` as a static site at your Pages URL. Anyone can visit it.

Steps 4–5 happen automatically in the cloud after you push — you don't need to build locally first. Local build is just for previewing.

## 3. How to Update Your Garden (day-to-day)

The golden workflow is just two actions:

```bash
# 1. Write or edit Markdown files in content/
# 2. Then:
npx quartz sync
```

That's it. Two steps. `sync` pulls, stages, commits, and pushes. GitHub handles the rebuild + deploy. Within ~1–2 minutes your site updates.

### Previewing before you push (recommended for big changes)
```bash
npx quartz build        # generate public/
npm run docs            # or npx quartz build --serve -d docs  (serves locally)
# open http://localhost:3000 in your browser to review
```
Once it looks right, push with `npx quartz sync`.

## 4. Things Worth Knowing

### The graph view / backlinks (why notes connect)
- The graph and "Backlinks" are driven by **wikilinks**: `[[Note Name]]`.
- A note only gets an edge in the graph if *another* note links to it with `[[...]]`.
- Link generously! `[[Note Name]]` or `[[Note Name|display text]]`.
- Image embeds use `![[filename.png]]` (Obsidian style) — resolved relative to the note's folder.

### Math / LaTeX
- Display math: `$$ ... $$` **alone on its own line**.
- Inline math: `$...$`.
- ⚠️ `$$` must sit on its own line — never glued to the end of a sentence or list item, or KaTeX can swallow the rest of the file (a parser error we hit once).

### Key config file: `quartz.config.yaml`
- `baseUrl: ahmed-bahlaoui.github.io/quartz` — must match your Pages URL (it does). Needed for RSS/sitemap.
- Plugin enable/disable switches live here.
- We **disabled** `@quartz-community/cname` — it emitted a `CNAME` meant for a custom domain, but you're using the default GitHub Pages URL. Leave it off.

### The graph plugin
Enabled in config as `@quartz-community/graph`. On any note the right sidebar shows a local **Graph View**; the globe button (bottom-left) opens the full global graph. Make it more connected simply by adding `[[links]]` between related notes.

### `public/` is regenerated, don't hand-edit
Anything built into `public/` is overwritten on every build. Always edit the source `.md` in `content/`, never the generated HTML.

### Git branch: `v5`
Your default branch is named `v5` (this matches Quartz 5 convention, not "version 5" chaos — it's just the branch name the workflows watch). The deploy workflow triggers on pushes to `v5`, which is what you're on. Keep using `v5`.

### Custom domain (later, if you want)
If you ever want `example.com` instead of `*.github.io/quartz/`:
1. Re-enable the CNAME plugin (or use the Pages custom-domain settings).
2. Set `baseUrl` to your domain in `quartz.config.yaml`.
3. Add DNS records per GitHub's docs.
For now you don't need this.

### The deployment environment quirk (what we fixed)
- GitHub Pages releases are governed by a "Pages environment".
- If a stale `github-pages` environment exists (often inherited from a fork) with a branch restriction that doesn't include `v5`, deploys fail with:
  > `Branch "v5" is not allowed to deploy to github-pages due to environment protection rules.`
- Fix: **Settings → Environments → delete the `github-pages` environment.** The workflow recreates it correctly on next run.

## 6. Quick Workflow Cheat-Sheet

| What I want | What I do |
|---|---|
| Write a new note | create `content/<folder>/<name>.md`, then `npx quartz sync` |
| Edit a note | edit the `.md`, then `npx quartz sync` |
| Preview locally first | `npx quartz build` + serve, then sync |
| Add a link between notes | add `[[Note Name]]` in the `.md` body |
| Add images | put them in an `images/` folder, embed `![[file.png]]` |

Everything else is auto-magic on GitHub.
